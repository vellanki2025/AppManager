What the user sees when an app is updated

The service decides from vehicle state alone: never download or install while driving; when the vehicle is stationary, download and then install. It does not ask individual apps, or the system, what an app is doing.

Rules for the two cases

One decision table for the nightly 02:00 run and Update now. The thresholds are the defaults in Config; change them there rather than here.

Hold reasons

When a rule fails, the run persists WAITING with one BlockReason and rechecks 15 minutes later: DRIVING, BATTERY, NETWORK, STORAGE, or SYSTEM_STOP when WorkManager stops the worker. An unreachable catalogue is reported as NETWORK with the cause in the message. The reason goes to the log and the AIDL status; it never reaches a row in the UI, which shows four fields and a fixed three-word state.

Per-app install rules (not built)

An earlier design had the Release Manager set per-app install rules, delivered inside a signed manifest and evaluated at install time. That is not implemented, and the current cloud contract has no place for it: the catalogue returns an Manifest carrying packageName, versionCode, size and digest, and nothing else. The gate is the four rules above, the same for every app.

It is recorded here because the capability may still be wanted. Adding it would mean extending the manifest contract and giving the install gate a per-manifest rule set, on top of the baseline, which would still not be loosenable: driving and battery would continue to apply whatever a rule said.

Lifecycle events sent to Analytics

The service saves each event first, then sends it in a batch. Event names and fields are proposed and should be aligned with the Analytics schema.

Fields on every event

eventId (unique, for de-duplication), appId, releaseId, fromVersionCode, toVersionCode, trigger (auto_night or update_now), profileType (primary or secondary, Update now only), network (wifi, cellular or other), attempt, reason (failures), heldReason (holds), ruleName (install_rule holds), timestamp. The vehicle is identified by its device certificate. No profile name or ID is sent.

Assumptions to confirm

  • Ignition position must come from the vehicle signal library alongside gear and speed. Two driving states cannot be derived without it: a car with the ignition off reports gear Park and zero speed exactly like one with the ignition on, so TURNED_OFF and ACCESSORY are otherwise indistinguishable from PARKED. RawDrivingSignals has the field; the library is not connected yet.
  • STOPPED, stationary but in gear, is permitted by decision (2026-11-05). It is the one permitted state that is not inherently safe: the vehicle can move again without warning. A download is covered, since the watcher pauses it as soon as the state becomes DRIVING, but a commit already started has no equivalent check.
  • Decided 2026-10-12: driving blocks both download and install. A download in progress pauses when driving starts, keeps its partial file and offset, and resumes after 10 continuous seconds of a permitted state. Neither half is tied to a time window any more: one run does both, at 02:00 or on demand.
  • The cloud contract is still our proposal. Manifest, SignedUrl and the two-call split have no backend sign-off, and the download engine has never run against a real server.
  • Privileged install is unverified on a head unit. Only INSTALL_NEEDS_USER_ACTION has been seen on a bench, which is the correct unprivileged answer; the silent path needs the privapp allowlist for com.lucid.appmanager in the system image.
  • When space is short, an app that is already downloaded is installed first (if its rules allow) and its APK deleted. An APK that has not been installed is never deleted to make space, except when a newer version of the same app replaces it.
  • Vehicle state is the only gate for installs, apart from the manifest rules: driving is a strict no, parked is allowed. The service never asks apps what they are doing, so Navigation or music can stop when an update installs while parked. Tapping Update now counts as the user's consent, and the message appears when the install starts, with no countdown.
  • Apps restart when updated, so app teams should save their own state.
  • All numbers are placeholders: window 1 to 5 AM local time, auto needs WiFi of at least 2 Mbps, auto needs HV battery of at least 30% or charging, Update now needs at least 10% to download and 20% or charging to install, 12V minimum from the vehicle power team, free space of 2x the APK size, stall timeout 60 s, Park debounce 10 s.
  • Can the head unit wake at 02:00 (for example Garage Mode on Android Automotive)? If not, the run happens at the next opportunity after 02:00, which the 15 minute recheck already handles.
  • Updates are per vehicle, not per profile. The service runs in the system user. Primary and secondary profiles can use Update now; guest is view-only.
  • One run covers both halves: the download gate checks driving, battery, network and storage; the install gate re-reads driving and battery only. There is no separate install window.
  • Decided 2026-10-12: cellular consent lives in Settings, not in the Update now flow. The "WiFi or cellular" option is shown only when the vehicle has a connectivity subscription; without one, downloads are WiFi only.
